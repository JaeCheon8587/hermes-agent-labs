1. 목표와 핵심 원칙

목표

목표는 Hermes PM/Kanban 운영환경을 만드는 것이다. 테스트 프로젝트 자체를 보존하는 것이 아니다.

예: HermesTest는 disposable smoke-test workspace다.

PM 역할

project_manager는 Slack-facing 오케스트레이터다. 직접 코드를 읽고 고치는 주체가 아니라, 계획·승인·분해·라우팅·최종보고를 맡는다.

Worker 역할

설계/구현/리뷰는 내부 worker 프로필이 Kanban task로 수행한다. 사용자는 worker와 직접 대화하지 않는다.

쉽게 말하면: 사용자는 Slack에서 PM에게만 말한다. PM은 일을 잘게 나누고, 내부 작업자들에게 티켓을 나눠주고, 작업 결과와 리뷰 결과를 모아서 다시 사용자에게 보고한다.

3. Slack에서 PM에게 메시지를 보냈을 때

사용자가 Slack에 “@PM Step 2로 도서 조회 API만 진행해. 먼저 설계/작업분해를 하고 내 승인 전엔 구현하지 마.” 같은 메시지를 보내면 아래 순서로 흘러간다.

sequenceDiagram
  autonumber

  participant Slack as Slack
  participant Gateway as project_manager Gateway
  participant PM as project_manager LLM
  participant Tool as pm_workflow_tool
  participant Plan as PM Plan Store
  participant Board as Kanban DB

  User->>Slack: @PM 요청 전송\n"설계 먼저, 승인 전 구현 금지"
  Slack->>Gateway: Socket Mode event 전달
  Gateway->>PM: Slack 메시지 + session context 전달
  PM->>PM: 요청 의도 판단\n범위, 경로, 승인 조건, worker 제한 해석
  PM->>Tool: pm_create_plan(request, summary, tasks, contract)
  Tool->>Tool: plan_kind / task graph / assignee / contract 검증
  Tool->>Plan: status=awaiting_pm_approval 저장
  PM-->>Slack: 설계/작업분해 계획 보고 + 승인 요청

  User->>Slack: "승인" 또는 "계속 진행"
  Slack->>Gateway: 승인 메시지 전달
  Gateway->>PM: 승인 의도 전달
  PM->>Tool: pm_execute_plan(plan_id)
  Tool->>Board: architect/design task 생성
  Board->>Arch: dispatcher가 task claim/spawn
  Arch->>Arch: Claude runner로 설계 artifact 작성
  Arch->>Board: task complete + manifest/evidence
  Cron->>Plan: design ready 상태 감지/표시
  Cron-->>Slack: 설계 검토 완료, 사용자 설계 승인 요청

중요: Slack 메시지 하나가 바로 구현으로 가지 않는다

현재 목표는 안전한 운영환경이므로, PM은 먼저 계획을 만들고 승인받는다. 그 다음에도 architect가 설계 산출물을 만들고, 다시 사용자가 설계를 승인해야 구현 task가 만들어진다.

PM이 Slack 메시지를 해석할 때 보는 것

  • 요청 범위: 어떤 기능/단계만 하라고 했는가?
  • 경로 기준: 작업 대상 project path는 어디인가?
  • 승인 조건: “승인 전 구현 금지”, “설계 먼저 보고” 같은 제약이 있는가?
  • worker 제한: 어떤 프로필/모드가 허용되는가?
  • 산출물 기대값: design artifact, implementation artifact, verification artifact, final report가 필요한가?
  • plan_kind: 이 요청은 design-only인가, mapping인가, execution인가?

4. 설계 승인과 실행 승인 흐름

이 운영환경의 핵심은 두 번의 승인이다. 첫 번째는 “PM 계획을 실행해도 되는가?”, 두 번째는 “architect 설계를 보고 실제 구현으로 넘어가도 되는가?”다.

stateDiagram-v2
  [*] --> DraftRequest: Slack 요청 수신
  DraftRequest --> AwaitingPMApproval: pm_create_plan\n계획/작업분해 저장
  AwaitingPMApproval --> DesignInProgress: 사용자 PM 계획 승인\npm_execute_plan
  DesignInProgress --> DesignRepair: architect artifact contract 실패
  DesignRepair --> DesignInProgress: repair retry 1~2회
  DesignRepair --> Blocked: 2회 실패 또는 복구 불가
  DesignInProgress --> AwaitingDesignApproval: design artifact 통과\npm_mark_design_ready 또는 notifier
  AwaitingDesignApproval --> DesignRevision: 사용자 수정 요청
  DesignRevision --> DesignInProgress: architect 재작업
  AwaitingDesignApproval --> ExecutionInProgress: 사용자 설계 승인\nexecution plan 또는 follow-up 실행
  ExecutionInProgress --> ReviewInProgress: implementer 완료
  ReviewInProgress --> FinalSynthesis: reviewer verdict pass/concern 정책 통과
  ReviewInProgress --> Blocked: reviewer blocked/fail 또는 증거 부족
  FinalSynthesis --> Completed: final report metadata/artifact 통과
  FinalSynthesis --> Blocked: reviewer evidence/final report gate 실패
  Blocked --> ExecutionInProgress: 재지시/수정/언블록
  Completed --> [*]

plan_kind 기준

plan_kind의미허용되는 task끝나는 지점
design설계만 한다architect만설계 승인 대기 또는 approved
mapping승인된 설계를 실제 repo 경로에 매핑한다architect만실행 scope 확정 전
execution승인된 설계/scope를 구현·리뷰·최종보고한다implementer, reviewer, PM finalcompleted 또는 blocked
staged구버전 호환형 staged flowarchitect → implementer → reviewer → PM final새 흐름에서는 design/mapping/execution 분리가 권장

backend-reviewer 승인된 설계 snapshot, approved scope, 구현 artifact, 변경 파일, 테스트/빌드 결과 설계 정렬성, scope 준수, acceptance criteria 충족, evidence 충분성, open risk 여부 .soul/artifacts/verification/*_verification.md, reviewer_result metadata verdict가 pass/concern/blocked 중 하나이고, acceptance_checks/evidence/scope_status가 구조적으로 채워져야 함

cron notifiers PM plan store, Kanban DB, task_events, artifacts, dedupe state 새 design-ready/completion/blocked 이벤트인지, 이미 보고한 이벤트인지, scope phase sync가 필요한지 Slack 알림 또는 무출력, ~/.hermes/state/*.json dedupe state 새 이벤트 없으면 stdout 0 bytes로 조용히 종료

7. 판단 기준과 게이트

이 시스템은 “agent가 잘했다고 말했는가?”가 아니라, 파일·manifest·metadata·task 상태가 contract를 만족하는가?를 기준으로 움직인다.

  Start[Task complete 요청] --> Find[PM plan에서 task phase 찾기]
  Find --> Phase{phase?}
  Phase -->|architect| A1[Claude manifest 존재 확인]
  A1 --> A2[design artifact contract 확인]
  A2 -->|실패| Repair{repair 가능?}
  Repair -->|1~2회 가능| A3[repair prompt로 재실행]
  A3 --> A2
  Repair -->|불가/초과| Block[blocked]
  A2 -->|통과| Done[done]

  Phase -->|implementer| I1[runner manifest 확인]
  I1 --> I2[implementation artifact/evidence 확인]
  I2 --> I3[approved scope 밖 변경 여부 확인]
  I3 -->|통과| Done
  I3 -->|실패| Block

  Phase -->|reviewer| R1[reviewer_result metadata 확인]
  R1 --> R2[design acceptance coverage 확인]
  R2 --> R3[validated_artifacts/evidence/scope_status 확인]
  R3 -->|pass/concern 정책 통과| Done
  R3 -->|blocked/fail/증거 부족| Block

  Phase -->|final| F1[reviewer_result 재검증]

  F2 --> F3[final artifact sections 확인]

  F3 -->|실패| Block

8. Cron notifier와 Slack 보고

PM workflow의 일부 보고는 agent가 매번 생각해서 보내는 것이 아니라, no_agent=true cron script가 runtime state를 보고 결정한다.

sequenceDiagram
  autonumber
  participant Cron as Hermes Cron Scheduler
  participant Script as pm_* runtime script
  participant Plans as PM Plan Store
  participant Board as Kanban DB / Events
  participant State as ~/.hermes/state/*.json
  participant Slack as Slack PM Channel

  Cron->>Script: every 1m 실행(no_agent=true)
  Script->>Plans: plan 상태 조회
  Script->>Board: task/status/event 조회
  Script->>State: dedupe 상태 조회
  alt 새 design-ready/completion/blocked 이벤트 있음
    Script->>State: last_event/reported 기록
    Script-->>Cron: Slack-ready text stdout
    Cron-->>Slack: stdout 그대로 전달
  else 새 이벤트 없음
    Script-->>Cron: stdout 없음
    Cron-->>Slack: 아무것도 보내지 않음
  end

현재 runtime helper script

  • pm_design_ready_notifier.py: architect 설계가 준비되면 설계 승인 요청을 Slack에 보낸다.
  • pm_kanban_completion_notifier.py: PM final task 완료 후 최종 완료 보고를 Slack에 보낸다.
  • pm_kanban_blocked_notifier.py: workflow task가 blocked로 전환되면 이유와 다음 액션을 Slack에 보낸다.
  • pm_scope_phase_sync.py: implementer → reviewer, reviewer → final 사이에서 approved_scope.json을 phase에 맞게 동기화한다.

운영 포인트: cron script는 새 이벤트가 없으면 아무것도 출력하지 않는다. 그래서 1분마다 실행돼도 Slack 스팸이 발생하지 않는다.

9. 실패/blocked/repair 흐름

flowchart TD
  Fail[문제 발생] --> Kind{문제 종류}
  Kind -->|architect artifact 형식 문제| Repair1[repair prompt 1회]
  Repair1 --> Check1{contract 통과?}
  Check1 -->|예| Continue[계속 진행]
  Check1 -->|아니오| Repair2[repair prompt 2회]
  Repair2 --> Check2{contract 통과?}
  Check2 -->|예| Continue
  Check2 -->|아니오| Block1[blocked: artifact_contract_failed]

  Kind -->|worker auth/preflight 문제| Preflight[preflight_blocked]
  Preflight --> FixAuth[profile auth/gateway 복구]
  FixAuth --> Retry[pm_execute_plan 또는 approve_design retry]

  Kind -->|scope mismatch| ScopeBlock[blocked]
  ScopeBlock --> ScopeSync[pm_scope_phase_sync 또는 execution scope 수정]
  ScopeSync --> Unblock[unblock/retry]

  Kind -->|reviewer concern| Concern[concern follow-up]
  Concern --> Decide{추가 구현 필요?}
  Decide -->|예| NewImpl[새 implementer card]
  Decide -->|아니오| FinalRisk[final report open_risks에 반영]

blocked를 실패로만 보지 않는 이유

이 운영환경에서 blocked는 “망했다”가 아니라 안전하게 멈췄다는 뜻이다. 구현 범위를 벗어났거나, 증거가 부족하거나, 사용자의 추가 판단이 필요한 경우에는 계속 진행하지 않고 멈추는 것이 정상이다.

10. 운영자가 기억할 것

runtime script sync

cd ~/.hermes/hermes-agent
scripts/sync-pm-workflow-runtime.sh

canonical source는 repo의 scripts/pm-workflow/, runtime copy는 ~/.hermes/scripts/.

짧은 운영 원칙

  1. 사용자는 PM에게만 말한다.
  2. PM은 승인 전 구현하지 않는다.
  3. 설계는 architect가 artifact로 남긴다.
  4. 구현은 implementer가 승인된 scope 안에서만 한다.
  5. 리뷰는 reviewer가 독립적으로 한다.
  6. 최종 보고는 reviewer 결과를 숨기거나 왜곡하지 않는다.
  7. PM의 말보다 실제 Kanban task와 artifact를 믿는다.
  8. 테스트 프로젝트는 disposable이다. 운영환경 code/docs/scripts만 repo에 보존한다.
