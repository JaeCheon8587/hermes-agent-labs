PM Workflow Productization Phase 1 Completion

Hermes 기반 PM 중심 staged workflow의 1차 제품화 작업이 완료되었음을 기록한다. 이 문서는 개념 검증이 아니라, 실제 라이브 스모크 런과 코드/테스트 기준으로 어떤 기능이 안정화되었는지 정리한다.

Date: 2026-05-23 Status: Phase 1 Complete Validated Runs: v7, v9, v10 Focus: Core workflow hardening

Executive Summary

현재 시스템은 사용자 → PM → architect → design approval → implementer → reviewer → final → PM 보고 구조를 실제로 수행할 수 있다. v10에서는 architect 완료 후 설계 승인 요청 알림이 자동 발송되는지까지 재검증되었고, 최종 완료 보고도 정상적으로 도착했다. 따라서 PM 중심 staged workflow의 핵심 메커니즘은 실사용 가능한 수준에 가까워졌다.

완료된 핵심 목표

  • plan-only 생성
  • design gate 강제
  • follow-up task 자동 생성
  • review/final evidence 생성
  • PM 최종 보고 자동화

이번 1차에서 실제 고정한 문제

  • core phase transition 누락
  • scope phase sync 의존성
  • completion notifier false positive
  • explicit contract schema mismatch
  • design approval notification 누락

핵심 원리
이 시스템의 본질은 “프롬프트로 권고”가 아니라 “Python이 상태와 전이를 강제”하는 구조다. PM이 자연어 계획을 제안하더라도, 실제 실행 가능 여부는 workflow contract, phase별 allowed path, evidence 요구사항, Kanban task lineage, final validation 규칙이 함께 통과할 때만 성립한다.

Core Workflow Operating Principle

Phase 1에서 구현한 코어는 하나의 "AI 팀 대화"를 흉내 내는 구조가 아니라, plan state + Kanban task state + workflow contract + evidence artifact를 함께 사용하는 결정적 workflow engine에 가깝다. 모델은 각 phase의 작업을 수행하지만, phase를 건너뛰거나, 승인 없이 구현하거나, evidence 없이 완료 처리하는 것은 Python 로직이 막는다.

진입점
사용자 요청은 PM plan으로 먼저 수집되고, 바로 구현으로 가지 않는다.
상태 저장
pm_plans.json이 plan-level source of truth 역할을 수행한다.
실행 단위
실제 작업 수행은 Kanban task로 분해되어 profile별 worker에게 할당된다.
제약 조건
contract.json이 deliverable, allowed path, evidence, phase graph를 명시한다.
완료 판정
final summary만으로 끝나지 않고 deliverable/evidence/lineage 검증이 선행된다.

Python / State Machine / Contract / Evidence

문서에서 반복해서 나오는 Python/state machine/contract/evidence는 단순 슬로건이 아니라, 실제로 역할이 분리된 네 개의 제어층을 뜻한다. 이 구조 때문에 PM workflow는 “모델이 알아서 잘 해주길 기대하는 시스템”이 아니라 “실행 가능 상태만 다음 단계로 전이시키는 시스템”이 된다.

1. Python

Python 코드는 실제 집행자다. plan 생성, phase 전이, validator, notifier, Kanban completion hook이 모두 여기 있다. 모델이 무엇을 말하든, Python이 허용하지 않으면 다음 phase로 넘어가지 못한다.

2. State Machine

plan은 awaiting_approval, design_in_progress, awaiting_design_approval, executed, completed, superseded 같은 상태를 가진다. 각 상태는 “사용자가 무엇을 해야 하는지”와 “어떤 worker task를 만들 수 있는지”를 결정한다.

3. Contract

contract는 자연어 요구사항을 runtime 규칙으로 변환한 결과다. 대표 필드는 expected_deliverables, phase_allowed_paths, required_tasks_by_phase, required_evidence_by_phase다.

4. Evidence

evidence는 “진짜로 그 phase가 수행되었는가”를 증명하는 산출물이다. design, implementation, verification, final report artifact가 여기에 속한다. completion은 evidence가 없으면 통과하지 않는다.

"invalid phase or path" .-> X D -. "missing evidence" .-> X end
이 다이어그램의 의미
위 그림은 completion hook 내부 순서도가 아니다. 이것은 PM workflow가 의존하는 상위 제어 레이어를 보여주는 아키텍처 다이어그램이다. 즉 Plan state machine, Contract rules, Worker execution scope, Evidence artifacts, Completion validation는 훅이 읽고 갱신하는 대상이지, 훅 함수 내부에서 한 줄씩 실행되는 절차를 뜻하지 않는다.
왜 중요한가
동일한 모델이라도 prompt만 바꾸면 행동이 흔들릴 수 있다. 반면 이 구조에서는 contract가 파일 경로와 evidence 의무를 제한하고, state machine이 승인 없는 전이를 막고, completion validator가 산출물/증빙 부재를 최종 차단한다.

Detailed Core Mechanics

Plan layer

  • PM은 먼저 plan을 제안한다.
  • plan에는 task graph와 contract가 묶인다.
  • 사용자 승인 전에는 실행 task를 만들지 않거나 architect만 만든다.

Kanban layer

  • 실행은 Kanban task 단위로 분해된다.
  • architect / implementer / reviewer / final lineage가 남는다.
  • worker 완료/blocked 이벤트가 다음 phase 전이의 입력이 된다.

Scope layer

  • .soul/approved_scope.json는 현재 actionable phase snapshot이다.
  • implementer 완료 시 reviewer scope가, reviewer 완료 시 final scope가 export된다.
  • scope mismatch가 나면 worker는 blocked 되고 Hermes가 알림을 보낸다.

Validation layer

  • reviewer completion은 verdict schema를 만족해야 한다.
  • final task는 reviewer_result.verdict, reviewer_result.scope_status, reviewer_result.evidence를 다시 검사한다.
  • reviewer verdict가 blocked이거나 scope가 out-of-scope면 final handoff 자체가 생성되지 않는다.

어디서 강제되는가: 실제 코드 레벨 enforcement

이 문서에서 말하는 core transition은 추상 개념이 아니라, 특정 completion hook와 PM workflow 함수에서 강제된다. 핵심은 task done 이벤트가 발생했을 때 Python이 완료된 task를 하나의 입력 payload처럼 읽고, 그 task의 metadata를 기반으로 미리 정의된 transition callback을 dispatch한다는 점이다.

Event source
worker가 task를 done 처리하면 Kanban completion path가 즉시 실행된다.
Hook entry
hermes_cli/kanban_db.py에서 completion 후 handle_completed_pm_workflow_task(conn, task_id)를 호출한다.
Payload lookup
_find_plan_for_task()가 task_id를 기준으로 해당 task의 plan, key, phase, follow-up lineage를 역추적한다.
Dispatch key
핵심 분기 기준은 자연어가 아니라 phase == architect|implementer|reviewer 같은 deterministic metadata다.
Architect callback
awaiting_design_approval 상태 전이, design_status/design_summary/design_ready_at 기록, contract 재기록.
Implementer callback
_export_approved_scope(plan, "reviewer", reviewer_task_id, ...)로 reviewer phase snapshot 생성.
Reviewer callback
reviewer metadata(verdict, scope_status, evidence, changed_files)를 읽고 final handoff 허용 여부를 결정한다.
Final gate
final completion 시 approved_scope.json의 reviewer_result를 다시 읽어 verdict=pass, scope_status=within_allowed_paths, non-empty evidence를 강제한다.

Reviewer verdict schema + final handoff gate

reviewer는 자유 텍스트 요약만 남기면 안 된다. completion metadata에 최소 verdict, summary, evidence, changed_files, scope_status가 있어야 하며, blocked verdict일 때는 blocked_reason도 필요하다. 이 구조화된 reviewer_result가 final phase의 입력 계약이 된다.

Reviewer schema
verdict ∈ {pass, concern, blocked}, non-empty evidence, scoped changed_files, normalized scope_status.
Pass path
reviewer verdict가 pass이고 scope_status == within_allowed_paths이면 approved_scope.json에 reviewer_result를 싣고 final phase를 export한다.
Blocked path
reviewer verdict가 blocked이거나 scope_status == out_of_scope이면 PM은 review_status=blocked로 기록하고 final handoff를 만들지 않는다.
Final validator
final task completion 시 Hermes는 reviewer_result.verdict, reviewer_result.scope_status, reviewer_result.evidence를 다시 읽고, 이어서 report_summary, user_report, delivered_artifacts, open_risks 기반 final report schema도 검증한다. 또한 required_artifacts 포함 여부, 각 delivered artifact의 실제 파일 존재, 그리고 최종 report artifact 안의 필수 섹션(# Final Report, ## Summary, ## Delivered Artifacts, ## Open Risks) 존재까지 확인한다.

PM / Reviewer Developer Tabs

아래 탭은 운영 관점이 아니라 구현 관점 문서다. PM과 Reviewer가 각각 어떤 입력을 읽고, 어떤 상태 전이와 산출물을 만들며, 어느 함수에서 품질 게이트가 강제되는지 분리해서 설명한다.

PM 동작 메커니즘

PM은 코드를 직접 읽는 구현자가 아니라, plan/contract/approved-scope를 관리하는 orchestrator다. 핵심 책임은 사용자 요청을 staged workflow로 번역하고, 각 phase의 worker handoff가 유효한지 Python validator로 강제하는 것이다.

pm_workflow_tool.py의 plan/contract builder, kanban_db.py completion hook, final validator

plan approval 요청, design approval 요청, final report 전달

PM UML의 핵심은 event source가 항상 task done이며, PM reasoning이 아니라 completion hook + contract validator가 phase 진입 여부를 결정한다는 점이다.

Reviewer 동작 메커니즘

Reviewer는 구현자와 별개 컨텍스트에서 승인된 설계 스펙을 읽고, 그 설계와 실제 산출물의 정렬성을 구조화된 verdict metadata로 제출하는 품질 게이트다. reviewer는 architect의 사고과정을 읽지 않고도 design_spec, expected_deliverables, acceptance_criteria 기반으로 검증을 수행한다.

입력
approved_scope.json의 review snapshot, design_spec, implementation artifacts, verification evidence path
필수 출력
verdict, summary, evidence, changed_files, scope_status, validated_artifacts, acceptance_checks, unmet_requirements, design_alignment_summary
핵심 함수
build_worker_context(), _validate_reviewer_completion_metadata(), PM reviewer callback, final consistency validator
품질 게이트
verdict schema 검사, changed_files allowed path 검사, blocked verdict 시 blocked_reason 요구, design-alignment fields non-empty 검사
downstream 영향
reviewer_result가 final phase의 입력 계약이 되며, unmet requirement가 남으면 final completed 보고가 차단된다

Reviewer 입력 상세

review snapshot
review mode, required verdict fields, required evidence, allowed verdict values 같은 reviewer 계약의 본체다. reviewer는 이 스냅샷을 기준으로 무엇을 반드시 제출해야 하는지 결정한다.
design_spec
승인된 설계 결과물의 요약 계약이다. 최소한 design artifact path, expected deliverables, acceptance criteria를 포함하며 reviewer가 "무엇을 기준으로 검증할지"를 정의한다.
implementation artifacts
구현자가 남긴 코드/문서/산출물이다. reviewer는 이 실제 결과물을 design_spec과 대조한다.
verification evidence path
검증 산출물을 어디에 남겨야 하는지 알려주는 경로다. reviewer의 evidence는 단순 텍스트가 아니라 artifact path로 남겨져야 final 단계에서 재검사할 수 있다.

Reviewer 출력 필드 의미

필드 의미 실무적 해석
verdict reviewer의 최종 판정이다. 현재 계약상 pass, concern, blocked 중 하나다. pass는 final handoff 가능, concern은 follow-up 전제로 final 보고 가능, blocked는 final handoff 중단을 뜻한다.
summary 검토 결과의 짧은 요약이다. 사람이 reviewer 결과를 빠르게 이해하기 위한 한 줄 판정문이다.
evidence reviewer가 실제로 남긴 verification artifact 경로 목록이다. "검토했다"는 주장만으로는 안 되고, 실제 재검사 가능한 증빙 파일이 있어야 한다.
changed_files 검토 대상 변경 파일 목록이다. allowed path 범위 안에서만 작업했는지 scope gate가 이 목록으로 검사된다.
scope_status 변경 범위가 계약상 허용 경로 안인지에 대한 정규화된 상태다. 대표적으로 within_allowed_paths 또는 out-of-scope 계열 값을 가지며, out-of-scope면 final handoff가 막힌다.
validated_artifacts reviewer가 실제로 검토 완료했다고 인정한 산출물 목록이다. 어떤 deliverable을 확인했는지 명시해 final/report 단계에서 정합성 검사가 가능해진다.
acceptance_checks acceptance criteria별 점검 결과다. 각 요구사항이 pass인지, concern인지, blocked인지 구조화해서 남기는 체크리스트 역할을 한다.
unmet_requirements 아직 충족되지 않은 요구사항 목록이다. 이 값이 비어 있지 않으면 final에서 completed 보고를 그대로 허용하면 안 된다.
design_alignment_summary 설계와 구현의 정렬 상태를 서술형으로 요약한 필드다. 최종 보고에서 reviewer가 본 정렬 상태를 사용자에게 설명하는 근거가 된다.

Reviewer verdict 해석 규칙

pass
설계 스펙 대비 핵심 deliverable과 acceptance criteria가 충족되었고, scope도 허용 범위 안에 있다고 reviewer가 판단한 상태다. 이 경우 final scope export가 가능하다.
concern
완전히 막을 정도는 아니지만 남은 위험, follow-up, 주의사항이 있다는 뜻이다. final phase는 가능하지만 보통 needs_followup 성격의 보고와 연결된다.
blocked
설계 불일치, 중요한 acceptance 미충족, out-of-scope 변경 등으로 downstream 진행을 멈춰야 한다는 뜻이다. 이 경우 blocked_reason 같은 추가 근거가 필요하다.

Reviewer 품질 게이트가 실제로 막는 것

  • 필수 verdict field 누락
  • evidence/artifact 없이 "검토 완료"라고 주장하는 경우
  • 허용 경로 밖 파일 변경을 숨기는 경우
  • acceptance criteria 점검 없이 pass를 선언하는 경우
  • unmet requirement가 있는데도 final에서 completed로 포장하려는 경우

Canonical output templates

운영 시 PM/Reviewer/Final worker는 아래 골격을 그대로 따르는 쪽이 가장 안정적이다.

역할 권장 출력 형태 비고
PM plan summary + approval request + task breakdown 사용자 승인 단계에서는 자유 서술이 가능하지만, task breakdown과 acceptance criteria는 구조적으로 적는 것이 좋다.
Reviewer JSON metadata + verification artifact 가장 엄격한 구조화 출력이 필요하다. schema validator가 직접 읽는다.
Final final report markdown + final metadata 사용자용 자연어 보고와 machine-checkable metadata를 동시에 만족해야 한다. 
PM template
- Request summary
- Proposed scope
- Acceptance criteria
- Task breakdown
- Approval question

Reviewer template
- verification markdown artifact
- reviewer_result metadata JSON

Final template
- final report markdown artifact
- final_report metadata JSON

Final report metadata 예시

{
  "completion_status": "needs_followup",
  "report_summary": "Implementation completed with one documented follow-up.",
  "user_report": "The requested flow is implemented. Reviewer confirmed core acceptance criteria, but follow-up work remains for failure telemetry documentation.",
  "delivered_artifacts": [
    ".soul/artifacts/implementation/plan_x_implementation.md",
    ".soul/artifacts/verification/plan_x_verification.md",
    ".soul/artifacts/final/plan_x_final_report.md"
  ],
  "open_risks": [
    "Failure telemetry documentation is missing."
  ]
}

Blocked / Concern 운영 정책

verdict=pass
PM은 final handoff를 열어도 된다. 기본 목표는 completion_status=completed 보고다. 단, final report는 reviewer evidence와 scope 상태를 그대로 존중해야 한다.
verdict=concern
PM은 사용자 보고를 막지 않아도 되지만, follow-up을 숨기면 안 된다. 기본 정책은 completion_status=needs_followup와 non-empty open_risks를 사용해 잔여 위험을 드러내는 것이다. 현재 runtime은 reviewer concern 시 backend-specialist follow-up task를 자동 생성하고, 그 task id를 final scope/context에도 전달한다.
verdict=blocked
PM은 final handoff를 열지 않는다. 사용자에게는 진행 중단 사유와 다음 조치가 필요하다고 보고하고, 구현/설계 수정 루프로 되돌리는 것이 기본 정책이다. 현재 runtime은 blocked fix follow-up task를 자동 생성한다.
scope_status=out_of_scope
기술적 품질과 별개로 계약 위반으로 본다. reviewer가 blocked를 주지 않았더라도 운영 정책상 blocked로 취급하는 것이 안전하다.
unmet_requirements 비어있지 않음
final completed 보고 금지. PM은 unmet requirement를 open_risks나 follow-up 항목으로 승격해서 사용자에게 그대로 노출해야 한다.
권장 후속 액션
concern은 follow-up task 생성 검토, blocked는 implementer 또는 architect 수정 task 재진입이 기본이다.
flowchart TD A[Scope] --> B[Design Spec] B --> C[Implementation Artifacts] C --> D[Acceptance Checks] D --> E[Reviewer Metadata] E --> F[Final Scope Or Block]
flowchart LR A[Pass] --> B[Export Final Scope] C[Concern] --> D[Allow Follow Up] E[Blocked] --> F[Stop Final Handoff]
Reviewer의 본질
Reviewer는 자유 텍스트 리뷰어가 아니다. 설계 스냅샷을 기준으로 acceptance check 결과, 미충족 요구사항, 설계 정렬 요약을 구조화해서 남기고, 그 결과가 final PM 보고의 허용 범위를 결정하는 deterministic quality gate다.
